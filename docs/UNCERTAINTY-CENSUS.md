# Uncertainty census - reference-impl governance layer (2026-06-30)

An exhaustive per-slice audit by 8 parallel auditors. **355 uncertainties** catalogued: HIGH 48 / MEDIUM 189 / LOW 107 / INFO 11. This is a known-uncertainties register, not a defect list - most are honest limits, hedged comments, or untested paths, surfaced so nothing is hidden.


## HIGH-impact (48)

- **[backup-grounding] backup.py:6-8 module docstring** (overstated-claim) - 're-runs the tamper-evident chain on every org, so a restored trail proves it survived intact'
  - uncertain: 'proves it survived intact' overstates. chain.verify() proves the chain is internally consistent and (with DLE_CHAIN_KEY) HMAC-signed; it does NOT prove the SHA-matched file is the SAME trail that existed before (an attacker who fully re-forged a self-consistent chain + recomputed the manifest SHA + replaced the manifest passes both gates). Tamper-evidence is bounded by whether DLE_CHAIN_KEY is set and kept out of the backup. The docstring does not scope this.
  - resolve: Scope the claim: 'proves the restored chain is self-consistent and, if DLE_CHAIN_KEY was set and is not co-located with the backup, HMAC-authentic.' Note the manifest+SHA is integrity-only, not authenticity, in keyless mode.
- **[backup-grounding] backup.py:9-12 module docstring** (citation-provenance) - Mapping to SOC2 CC2.1, FDA 21 CFR 11.10(c), ISO 27001 9.1/9.2.2 + A.8.10, GDPR Art.32(1)(c), EU AI Act Art.19/26(6)
  - uncertain: These regulatory clause mappings are asserted in a docstring with no citation, no last_verified date, and are NOT routed through grounding.cite() the way the doctrine ('No citation, no check') demands. The clause numbers (e.g. ISO 27001 A.8.10, EU AI Act Art.26(6)) can go stale or be misattributed; they are not in GROUNDING and not gated by assert_fresh.
  - resolve: Add these regime clauses to a cited registry (GROUNDING or compliance.COMPLIANCE_FRAMEWORKS) with url+last_verified, gate via assert_fresh, and verify each clause maps to a retention/restorability obligation against the primary text.
- **[backup-grounding] backup.py:59 GovernanceStore(str(snap))** (assumption) - Opening the snapshot read-applies PRAGMA journal_mode=WAL (store.py:85)
  - uncertain: Constructing GovernanceStore on the just-written snapshot runs executescript(_SCHEMA) and sets WAL on the snapshot file (store.py:84-86). This MUTATES the snapshot AFTER its bytes were copied but the SHA is computed at line 67 from the on-disk file at that moment - so the SHA covers a snapshot that GovernanceStore may have already altered (WAL mode switch, schema re-apply). Whether the SHA is taken before or after these mutations depends on file-flush timing; the manifest SHA's exact coverage is uncertain.
  - resolve: Compute _sha256(snap) BEFORE opening any GovernanceStore on it, or open the snapshot strictly read-only (mode=ro URI) so the manifest SHA provably matches the restored bytes. Add a round-trip test: backup -> sha of snap == manifest sha at restore time.
- **[backup-grounding] backup.py:67 'sha256': _sha256(snap)** (edge-case) - SHA covers governance-{stamp}.db only, not -wal/-shm
  - uncertain: If the snapshot is in WAL mode (forced by store.py:85 when GovernanceStore opens it) there may be a sidecar -wal file whose contents are NOT in the SHA. A restore (shutil.copy2 of the single .db at line 104) copies only the main file; if data lived only in an un-checkpointed -wal, both the SHA and the restored DB silently miss it.
  - resolve: Checkpoint+TRUNCATE the snapshot (PRAGMA wal_checkpoint) and verify no sidecar holds committed data before hashing; or hash the logical DB content, not the file bytes.
- **[backup-grounding] backup.py:74 write_text(json.dumps(manifest))** (overstated-claim) - Manifest is plain JSON, unsigned
  - uncertain: The manifest carries the SHA but is itself unauthenticated. An attacker who replaces both snapshot and manifest (recomputing the SHA) defeats the SHA gate entirely; integrity here is only against accidental corruption / a tamper that misses the manifest. The docstring's 'tamper-evident' framing leans on the chain HMAC, but backup() does not sign the manifest with DLE_CHAIN_KEY.
  - resolve: HMAC-sign the manifest with the out-of-DB DLE_CHAIN_KEY (or detached signature) so a co-located manifest swap is detectable; state that the SHA alone is integrity-not-authenticity.
- **[backup-grounding] backup.py:104 shutil.copy2(src, dest)** (edge-case) - Restore copies only the single .db file
  - uncertain: copy2 copies one file; if the verified snapshot relied on a -wal sidecar (see line 67 item) the restore is incomplete. Also copy2 overwrites dest_db unconditionally - if dest_db is an existing live audit DB, it is clobbered with no backup-of-the-target and no confirmation. Destructive overwrite of a possibly-live evidence DB is unguarded.
  - resolve: Refuse to overwrite a non-empty dest without an explicit force flag; copy/verify sidecars; snapshot the target before overwrite.
- **[backup-grounding] tests/test_governance_backup.py whole file** (untested-path) - Test coverage: no concurrency, no WAL-checkpoint, no large DB, no malformed-manifest, no overwrite-live-dest, no empty-DB-restore, no same-second collision
  - uncertain: The 'safe with WAL', 'survived intact', and fail-closed claims are only smoke-tested on tiny single-org single-change DBs with distinct now= values. The HIGH-impact paths (WAL sidecar, manifest-swap, dest clobber, empty restore, malformed manifest, second-collision) are entirely untested.
  - resolve: Add tests for each path above; in particular a concurrent-writer WAL test to substantiate the headline 'safe with WAL' claim.
- **[chain-and-store] chain.py:3-9 (module docstring)** (overstated-claim) - "tamper-EVIDENT against an insider with database write access"
  - uncertain: The claim holds ONLY in keyed (HMAC) mode AND only if the out-of-DB key is genuinely out of the attacker's reach. An insider with DB write access who also has read access to the host filesystem (DLE_CHAIN_KEY_FILE) or process env (DLE_CHAIN_KEY) defeats it entirely. The docstring asserts the property without scoping the key-secrecy precondition in the same breath.
  - resolve: Add explicit precondition: tamper-evidence holds iff the signing key is inaccessible to the DB-write attacker (separate trust boundary / KMS / HSM). State that co-located env/file keys do not provide this.
- **[chain-and-store] chain.py:42 k.encode("utf-8")** (edge-case) - env key encoded as UTF-8 bytes
  - uncertain: The env-var key path uses UTF-8 encoding of the string, but the FILE path (line 45-47) uses raw read_bytes().strip(). The same logical key supplied via env vs file produces DIFFERENT key bytes if it contains non-ASCII or surrounding whitespace - chains signed one way fail to verify the other. No test covers env-vs-file key equivalence.
  - resolve: Normalize both paths to identical byte derivation (or document that env and file keys are NOT interchangeable). Add a test that the same secret via env and via file verifies the same chain.
- **[chain-and-store] chain.py:44 if kf and Path(kf).exists()** (edge-case) - key file existence check then read
  - uncertain: TOCTOU between exists() and read_bytes(); also if DLE_CHAIN_KEY_FILE is set but the path does NOT exist, the function silently returns None (keyless) with no error - a production deployment intending HMAC silently runs unsigned. CLAUDE.md says 'Set DLE_CHAIN_KEY in production'; a typo'd file path defeats this silently.
  - resolve: Raise or log loudly when DLE_CHAIN_KEY_FILE is set but unreadable/missing, instead of silent keyless fallback. Consider a strict 'require signed' mode.
- **[chain-and-store] chain.py:51-52 (_canonical)** (edge-case) - json.dumps(payload, sort_keys=True, separators=(",",":"))
  - uncertain: Canonicalization assumes payload is JSON-serializable with deterministic key sorting. (1) Non-str keys, sets, bytes, datetime, Decimal, NaN/Infinity will raise or produce non-canonical output. (2) sort_keys on mixed-type keys raises TypeError. (3) Unicode is not NFC-normalized, so visually identical payloads with different code points produce different MACs. (4) Float repr is platform/version dependent in edge cases. No validation of payload shape before MAC.
  - resolve: Validate/whitelist payload types; document that payload must be JSON-canonicalizable str-keyed dict; consider ensure_ascii and NFC normalization. Add tests for unicode, floats, nested dicts, non-str keys.
- **[chain-and-store] chain.py:70-80 (append)** (edge-case) - append reads chain_head, computes, writes chain row, then writes anchor - three separate commits, no transaction
  - uncertain: append() is not atomic: store.append_chain commits (store.py:164) and store.set_anchor commits separately (store.py:180). A crash between them leaves a chain row with a stale anchor -> verify reports 'truncated or rolled back' (false positive) on the next read. Also chain_head->append_chain has a TOCTOU under concurrency (two appenders can read the same head seq).
  - resolve: Wrap append_chain + set_anchor in a single transaction; serialize concurrent appends per-org (the PRIMARY KEY(org,seq) will raise IntegrityError on the racing writer - that path is untested).
- **[chain-and-store] chain.py:108 anchor signature check uses current _key()** (edge-case) - anchor_mac validated with the key read at verify time
  - uncertain: If the verify-time key differs from the append-time key (rotation, or env not set during verify but set during append - e.g. CLI run without DLE_CHAIN_KEY), the anchor signature check fails and reports 'anchor signature invalid' - which a reader may misread as tampering rather than a key/env misconfiguration. signed flag is set from current key, so a chain APPENDED keyed but VERIFIED keyless reports signed=False and the keyless branch silently treats it as fine up to the anchor (line 96 keyless MAC won't match the HMAC entry_hash -> reports 'payload tampered' at seq 1). Misleading reason string for an env mistake.
  - resolve: Detect key-present-but-mismatched vs key-absent and report a distinct 'key mismatch / unsigned verification of a signed chain' reason instead of 'payload tampered'. Add a test verifying a keyed chain with the key removed at verify time.
- **[chain-and-store] store.py:14-21 (_tenant_key)** (heuristic-fp-fn) - isprintable()/isspace() visibility check rejecting zero-width/BOM
  - uncertain: Heuristic for 'visible string': `any(ch.isprintable() and not ch.isspace() for ch in key)`. (1) Some control chars are not isprintable so a key of only control chars is rejected (good) but (2) characters that ARE isprintable but visually confusable/RTL-override (e.g. U+202E) PASS and can create homoglyph/spoofed tenant ids. (3) NFC normalization is not applied, so 'caf?' (composed) and 'caf?' (decomposed) are DISTINCT tenants - a cross-tenant isolation gap via unicode normalization.
  - resolve: NFC-normalize tenant keys before use; consider rejecting bidi/control/format categories; add tests for composed-vs-decomposed and RTL-override tenant collisions.
